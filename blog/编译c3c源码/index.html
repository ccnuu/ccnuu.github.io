发布于 2025年3月20日 · 更新于 2026年11月16日 · 7953 字
# C3C # C3 # CMake # AArch64 # 交叉编译

前言

2025 年第一次从源码构建 c3c 时，我卡在 Windows 下加载 LLVM 的步骤，最后通过修改 CMakeLists.txt 绕过。2026 年重新验证当前源码后，构建方式已经有所变化，原来的大段修改不再是推荐做法。

本文保留那次排错经历，并补充后来实际验证过的 Linux、AArch64 和 x86_64 交叉构建流程。重点不是记住几行命令，而是理解 CMake 正在找什么、为什么要找目标架构的 LLVM，以及生成了 AArch64 文件为什么仍可能无法运行。

c3c 源码（C/C++）
  -> CMake 配置构建
  -> C/C++ 编译器编译 c3c
  -> 链接 LLVM/LLD
  -> 得到可运行的原生 c3c
  -> 再编译 C3 项目

先选构建目标

“交叉编译 C3 程序”和“交叉构建 c3c 本体”是两件事，不要混在同一个问题里。

目标宿主编译器最终产物是否需要目标 LLVM
x86_64 上生成 AArch64 C3 程序现有 x86_64 c3cAArch64 程序不需要
在 AArch64 上原生构建 c3cAArch64 GCC/ClangAArch64 c3c需要 AArch64 LLVM/LLD
在 x86_64 上交叉构建 c3cAArch64 交叉 GCC/ClangAArch64 c3c需要 AArch64 LLVM/LLD

如果只是给 ARM64 开发板编译 C3 程序，现有 x86_64 c3c 已经内置 linux-aarch64 目标，只需要准备目标 sysroot。完整流程见 C3 交叉编译 AArch64。

本文后半部分讨论的是生成一个能在 AArch64 Linux 上运行的 c3c。

版本与环境

本文在 2026-11-16 对照了 C3 稳定版 0.8.6，交叉构建实测使用提交 fafd028c7，源码报告版本为 0.8.7 pre-release。

相关资源：

  • C3 官方文档
  • c3c 源码
  • C3 使用的 LLVM/LLD 预编译包

当前 c3c 的 CMake 允许 LLVM 19–24，默认版本为 23。LLVM 和 LLD 最好来自同一套构建。最省事的方式是让 CMake 下载 c3lang 维护的目标架构预编译包，而不是混用系统中版本不同的 LLVM 和 LLD。

还要区分两类 glibc 约束：

  • c3c 本体能运行，要求目标机的 glibc 不低于 c3c 实际使用的符号版本。
  • c3c 生成程序能运行，要求目标 sysroot 不新于目标机 glibc。

二者不能用同一个 linux-crt 配置互相替代。

Windows 原生构建

环境准备

  • Visual Studio 2022，勾选“使用 C++ 的桌面开发”
  • CMake
  • Git

在 Developer PowerShell 中进入源码目录。当前推荐使用仓库自带的 preset：

git clone https://github.com/c3lang/c3c.git
cd c3c

cmake --preset windows-vs-2022-release -DC3_FETCH_LLVM=ON
cmake --build --preset windows-vs-2022-release

产物位于 build\Release\c3c.exe。验证：

.\build\Release\c3c.exe -V
.\build\Release\c3c.exe compile .\resources\examples\hash.c3

C3_FETCH_LLVM=ON 表示由 CMake 下载对应的 Windows LLVM/LLD 包。它不会从源码编译整个 LLVM。

2025 年的旧排错记录

当时卡在：

Loading Windows LLVM libraries, this may take a while...

旧版 CMake 在 MSVC 下使用 LLVM_Windows、LLVM_Windows_debug 等 FetchContent 条目。当时的临时方案是注释自动下载，手动指定本地 LLVM 路径：

set(llvm_dir "D:/llvm-19.1.5-windows-amd64-msvc17-libcmt-dbg"
    CACHE PATH "Path to LLVM directory")

这类修改只适用于旧版 CMakeLists.txt。当前版本的结构已经变化，不应直接照搬，否则容易把新的 FetchContent 流程改坏。

如果需要手动准备 LLVM 目录，可以通过 FetchContent 的本地源目录直接指定：

cmake --preset windows-vs-2022-release `
  -DFETCHCONTENT_SOURCE_DIR_LLVM_ARTIFACT=D:/llvm-windows-amd64
cmake --build --preset windows-vs-2022-release

路径应指向解压后的 LLVM 根目录，通常能直接看到 lib/cmake/llvm。

Linux 原生构建

Manjaro 或 Arch Linux：

sudo pacman -S --needed cmake ninja git clang curl

Debian 或 Ubuntu：

sudo apt update
sudo apt install -y build-essential cmake git clang libcurl4-openssl-dev

通用构建步骤：

git clone --depth=1 https://github.com/c3lang/c3c.git
cd c3c

cmake -B build -S . \
  -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DC3_FETCH_LLVM=ON

cmake --build build -j"$(nproc)"
./build/c3c -V
./build/c3c compile resources/examples/hash.c3

CMake 会把标准库复制到 build/lib，因此可以直接从构建目录运行 ./build/c3c。

使用 C3_FETCH_LLVM=ON 时，CMake 会根据目标系统选择 LLVM 包。原生 AArch64 构建会下载 llvm-linux-aarch64.tar.xz，不会下载 x86_64 版本。

x86_64 交叉构建 AArch64 版 c3c

这一节的目标是生成一个只能在 AArch64 Linux 上运行的 c3c。本次已经在 Manjaro x86_64 上验证源码与交叉工具链能够生成正确的 AArch64 ELF。

实测环境：

Host:                 Manjaro Linux x86_64
Cross compiler:       aarch64-linux-gnu-gcc 16.1.0
Cross g++:            aarch64-linux-gnu-g++ 16.1.0
Cross glibc sysroot:  2.44
CMake:                4.4.4
Ninja:                1.13.2

安装交叉工具链

sudo pacman -S --needed \
  aarch64-linux-gnu-gcc \
  aarch64-linux-gnu-glibc \
  cmake \
  ninja

确认编译器目标：

aarch64-linux-gnu-gcc -dumpmachine
aarch64-linux-gnu-g++ -dumpmachine

两者都应输出 aarch64-linux-gnu。

CMake toolchain 文件

交叉构建不能只把 c3c 后缀改成 aarch64。CMake 必须知道目标系统、目标处理器以及库搜索范围：

# /tmp/c3c-aarch64-linux-toolchain.cmake
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)

set(CMAKE_C_COMPILER /usr/bin/aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER /usr/bin/aarch64-linux-gnu-g++)

set(CMAKE_FIND_ROOT_PATH /usr/aarch64-linux-gnu)
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)

其中 CMAKE_FIND_ROOT_PATH 相关的几行非常关键。缺少这些限制时，CMake 可能在 x86_64 主机上找到 /usr/lib/libcurl.so 或其他宿主库，配置阶段看起来正常，最终却因为架构不匹配而链接失败。

配置完整版

# 改成自己的 c3c 源码目录
C3C_SRC=/path/to/c3c
C3C_AARCH64_BUILD=/tmp/c3c-aarch64-llvm

cmake -S "$C3C_SRC" \
  -B "$C3C_AARCH64_BUILD" \
  -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=/tmp/c3c-aarch64-linux-toolchain.cmake \
  -DCMAKE_BUILD_TYPE=Release \
  -DC3_FETCH_LLVM=ON

配置输出中应出现：

Fetching Release LLVM artifact for linux-aarch64...

如果出现 linux-amd64，说明 toolchain 没有生效，不要继续构建，否则会链接宿主机 LLVM。

使用本地 LLVM 目录

如果需要统一管理构建依赖，可以准备 llvm-linux-aarch64.tar.xz，校验并解压后直接指定 FetchContent 源目录：

sha256sum /tmp/llvm-linux-aarch64.tar.xz

mkdir -p /tmp/llvm-aarch64
tar -xf /tmp/llvm-linux-aarch64.tar.xz -C /tmp/llvm-aarch64

cmake -S "$C3C_SRC" \
  -B /tmp/c3c-aarch64-llvm-local \
  -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=/tmp/c3c-aarch64-linux-toolchain.cmake \
  -DCMAKE_BUILD_TYPE=Release \
  -DFETCHCONTENT_SOURCE_DIR_LLVM_ARTIFACT=/tmp/llvm-aarch64

该目录必须能直接找到 lib/cmake/llvm 和 lib/cmake/lld。本地 LLVM 可以反复使用，清理构建目录后也不需要重新获取。

完整版构建命令：

cmake --build /tmp/c3c-aarch64-llvm-local -j2

仅 C 后端的快速验证

如果只想确认源码和交叉工具链能否工作，可以关闭 LLVM：

cmake -S "$C3C_SRC" \
  -B /tmp/c3c-aarch64-nollvm \
  -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=/tmp/c3c-aarch64-linux-toolchain.cmake \
  -DCMAKE_BUILD_TYPE=Release \
  -DC3_WITH_LLVM=OFF

cmake --build /tmp/c3c-aarch64-nollvm -j2

本次实测约 25 秒完成 111 个构建步骤，生成约 2.6 MB 的 AArch64 ELF。这个版本只有 C 后端，适合验证架构和启动环境，不等同于包含 LLVM 的官方完整版。

检查产物

x86_64 主机不能直接执行 AArch64 c3c，但可以先检查 ELF：

file /tmp/c3c-aarch64-llvm-local/c3c
readelf -h /tmp/c3c-aarch64-llvm-local/c3c | grep Machine
readelf -l /tmp/c3c-aarch64-llvm-local/c3c | grep interpreter

预期结果：

ELF 64-bit LSB pie executable, ARM aarch64
Machine: AArch64
[Requesting program interpreter: /lib/ld-linux-aarch64.so.1]

还要检查 c3c 本体要求的 glibc 符号版本：

readelf --version-info /tmp/c3c-aarch64-llvm-local/c3c \
  | grep -o 'GLIBC_[0-9.]*' \
  | sort -Vu

使用当前 Manjaro 交叉工具链构建的无 LLVM 版本，实测最高要求 GLIBC_2.38。如果目标板只有 glibc 2.31，即使文件架构正确，启动时仍会因缺少新符号失败。

此时必须使用匹配目标机的旧版交叉工具链和 sysroot 重新构建 c3c。项目里的 linux-crt、--linux-crt 只会影响 c3c 编译出的 C3 程序，不会降低 c3c 自身的 glibc 要求。

部署到 AArch64

交叉构建时不要直接执行 sudo cmake --install，否则可能把 AArch64 可执行文件安装到 x86_64 开发机的 /usr/local/bin，覆盖现有的 c3c。

先暂存到独立目录：

DESTDIR=/tmp/c3c-aarch64-stage \
  cmake --install /tmp/c3c-aarch64-llvm-local \
  --prefix /usr/local

安装结果为：

/tmp/c3c-aarch64-stage/usr/local/bin/c3c
/tmp/c3c-aarch64-stage/usr/local/lib/c3/

把可执行文件和标准库一起部署到目标机，然后在 AArch64 环境验证：

c3c -V
c3c compile resources/examples/hash.c3

如果要在目标机上使用 c3c project fetch、c3c vendor-fetch 等联网命令，目标系统还需要提供 libcurl。普通编译不要求 c3c 在构建时静态链接 libcurl。

常见问题

现象常见原因处理方式
找到 x86_64 libcurl 或其他宿主库CMake 没有隔离目标 sysroot设置 CMAKE_FIND_ROOT_PATH 和对应 ONLY 模式
仍下载 linux-amd64 LLVMtoolchain 没有生效检查 CMAKE_SYSTEM_PROCESSOR 和配置输出
文件是 AArch64，但主机无法运行宿主是 x86_64使用目标板或配置 qemu-user
目标机提示缺少 GLIBC_2.xxc3c 本体的 glibc 要求过高用匹配目标机的旧工具链和 sysroot 重建
交叉安装覆盖本机 c3c使用了宿主安装前缀使用 DESTDIR 暂存后部署
C 后端版本功能不完整使用了 C3_WITH_LLVM=OFF下载目标 LLVM/LLD，构建完整版

总结

构建时真正需要解决的是环境匹配。

最容易出错的四个地方是：

  1. CMake 是否选中了目标架构的 LLVM/LLD。
  2. CMake 是否把库搜索隔离到了 AArch64 sysroot。
  3. c3c 本体要求的 glibc 是否能在目标机运行。
  4. 部署时是否同时带上标准库，并把 AArch64 二进制安装到了正确位置。

理清这四点后，Windows 原生构建、Linux 原生构建和 x86_64 交叉构建 AArch64 版 c3c 本质上都是同一套 CMake 流程，只是编译器、LLVM 和 sysroot 的组合不同。
